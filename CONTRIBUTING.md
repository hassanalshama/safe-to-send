# Contributing

Safe to Send accepts focused fixes, new deterministic checks, test fixtures, documentation corrections, and compatibility improvements.

## Before opening a pull request

1. Search existing issues.
2. Keep the change narrow.
3. Add or update tests.
4. Run `npm run verify`.
5. Remove real personal, customer, credential, and company data from every fixture, log, screenshot, and commit.

## Adding a detector

A detector is not complete without all of the following:

- A stable rule ID.
- A clear statement of what the rule proves and what it only suggests.
- Severity and confidence justified by recipient exposure.
- A minimal intentionally unsafe synthetic fixture.
- A clean counterexample that must not trigger.
- Deterministic evidence and location.
- Practical remediation.
- A documented limitation.
- Tests covering detection, non-detection, malformed input, and relevant limits.

Avoid rules based only on a filename, application label, or broad keyword. Findings must help a user make a concrete sharing decision.

## Severity

- **High:** the file exposes concealed material, executable content, an uninspectable encrypted region, or a condition that should block sharing.
- **Medium:** the file retains review data, identity, hidden structure, or other material that may be inappropriate for the recipient.
- **Low:** a weak indicator or hygiene problem that still deserves review.
- **Info:** useful context that does not itself indicate a sharing risk.

Confidence is separate from severity. A high-impact geometry heuristic can be high severity with medium confidence.

## Fixtures

Fixtures are generated by `scripts/generate-fixtures.mjs`. Do not commit documents created from real work. Keep fixtures small, deterministic, and readable enough that a reviewer can map each inserted condition to an expected finding.

Regenerate fixtures with:

```bash
npm run fixtures
```

## Tests and checks

```bash
npm test
npm run check
npm run build
npm run verify
```

The repository intentionally has zero runtime dependencies. A new dependency needs a concrete security or correctness justification and should not be added merely to shorten code.

## Style

- Use standard JavaScript modules.
- Keep parsing bounded and fail closed on coverage.
- Prefer small pure functions.
- Preserve deterministic finding IDs and output order.
- Do not add telemetry, analytics, remote fonts, remote scripts, or network-backed detection.
- Do not claim that a clean result guarantees safety.

## Commit and pull-request content

State the problem, the exact behavior change, the evidence added, and the verification command. Avoid generated summaries and unrelated formatting changes.
